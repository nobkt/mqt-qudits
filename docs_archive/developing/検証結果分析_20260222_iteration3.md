## 問題の詳細分析

### Issue 1: ClassicalGKSLSimulator ≡ QuditGKSLSimulator

**問題**: 第2回反復でClassicalGKSLSimulatorのsolve_ivp(RK45)をStinespring+Trotter分解に
置換したが、これにより ClassicalGKSLSimulator は QuditGKSLSimulator と**完全に同一の
アルゴリズム**を使用するようになった。

**証拠**: 検証結果(20260222T091949Z)において、classical, qubit, quditの3シナリオが
小数点以下15桁まで完全に一致している：

```
classical: entropy = 0.030046553478841605, purity = 0.9924455995244283
qubit:     entropy = 0.030046553478841605, purity = 0.9924455995244283
qudit:     entropy = 0.030046553478841605, purity = 0.9924455995244283
```

**影響**: 3つのシミュレータが同一結果を出すため、相互検証（クロスバリデーション）として
機能しない。バグがあっても3つが同じ誤った結果を出すだけで検出できない。

**解決策**: ClassicalGKSLSimulatorを **Liouvillian超演算子の行列指数関数** (exact expm)
方式に変更する。これは:
1. Stinespring+Trotterとは**根本的に異なるアルゴリズム**
2. GKSL方程式の形式解 ρ(t) = exp(Lt)ρ(0) を数値的に厳密に計算
3. QDS (Quantum Dynamical Semigroup) 理論により exp(Lt) は常にCPTP
4. Trotter分解誤差がないため、Stinespring+Trotter結果の独立検証になる
5. ヒューリスティックでもfallbackでもない — GKSL方程式の標準的な解法

### Issue 2: `build_gksl_superoperator` のKronecker積引数順序バグ

**問題**: `stinespring_utils.py` の `build_gksl_superoperator` 関数は、
row-major (C-order) ベクトル化規約でKronecker積を構成しているが、
`vectorize_density_matrix` / `unvectorize_density_matrix` は
column-major (F-order) を使用している。

**詳細**: column-major ベクトル化では vec(AXB) = (B^T ⊗ A) vec(X) が成立する。

| 項 | 正しい column-major 形式 | コードの実装 |
|----|------------------------|-------------|
| vec(Hρ) | (I ⊗ H) vec(ρ) | (H ⊗ I) vec(ρ) |
| vec(ρH) | (H^T ⊗ I) vec(ρ) | (I ⊗ H^T) vec(ρ) |
| vec(LρL†) | (L* ⊗ L) vec(ρ) | (L ⊗ L*) vec(ρ) |
| vec(L†Lρ) | (I ⊗ L†L) vec(ρ) | (L†L ⊗ I) vec(ρ) |
| vec(ρL†L) | ((L†L)^T ⊗ I) vec(ρ) | (I ⊗ (L†L)^T) vec(ρ) |

全ての項でKronecker積の引数が逆転している。

**影響**: 現在このバグは**潜在的**であり、`build_gksl_superoperator` はどのシミュレータ
からも呼ばれていない。しかし、Issue 1の修正（ClassicalGKSLSimulatorのexpm化）で
この関数を使用するため、修正が必須。

### Issue 3: `build_trotter_step_classical` の同様のバグ

同じ `stinespring_utils.py` 内の `build_trotter_step_classical` も同一のKronecker積
引数順序バグを持つ。Issue 2と同時に修正する。

### Issue 4: ClassicalGKSLBosonSimulator の BDF ODE積分

**問題**: ClassicalGKSLBosonSimulator は `scipy.integrate.solve_ivp` の BDF法を使用。
BDFは陰的法でRK45より安定だが、密度行列のCPTP構造を保存する機構を持たない。

**現状**: N_molecules=2, n_max=1 の小システム（dim_total=36）では問題が顕在化していない。
検証結果では min_eigenvalue = 0.0 で完全にPASS。

**リスク**: システムが大きくなる（N_molecules=4, n_max=2 等）と、非ボソンの旧RK45と
同じCPTP違反が発生する可能性がある。

**解決策**: exact Liouvillian expm 方式に変更。dim_total^2 = 1296 なので計算量は問題ない。

### Issue 5: ボソンシミュレータの `rho_final` 不整合

**問題**: ボソンシミュレータが返す `rho_final` の空間が不統一：

| シミュレータ | rho_final | 次元 |
|------------|-----------|------|
| ClassicalGKSLBosonSimulator | ρ_el（電子系のみ、部分トレース済み） | 9×9 |
| QubitGKSLBosonSimulator | ρ_total（電子+フォノン拡張空間） | 36×36 |
| QuditGKSLBosonSimulator | ρ_total（電子+フォノン拡張空間） | 36×36 |

**影響**:
1. classical_boson と qubit_boson/qudit_boson の忠実度比較が不可能（次元不一致）
2. 検証スクリプトの validate_density_matrix がρ_totalに対して実行されるため、
   報告されるエントロピーが時系列データ（ρ_el由来）と不一致

### Issue 6: ボソンシミュレータの検証エントロピー不一致

**証拠**: qudit_boson の検証結果において：
```
時系列最終エントロピー（ρ_el由来）: 0.7290426960556708
検証エントロピー（ρ_total由来）:     0.73161075148684
```
0.35%の不一致は、ρ_totalのエントロピーとρ_elのエントロピーが異なることに起因する。
これはIssue 5の直接的帰結であり、Issue 5を修正すれば自動的に解消される。

## 修正方針

### 1. ClassicalGKSLSimulator → exact Liouvillian expm

- `build_gksl_superoperator` でGKSLリウビリアン超演算子 L を構築
- 伝播子 P = expm(L * dt) を1回だけ事前計算
- 各ステップ: vec(ρ') = P @ vec(ρ)
- 結果をunvectorizeして密度行列に復元

### 2. build_gksl_superoperator のバグ修正

- 全てのKronecker積の引数を column-major 規約に修正
- `np.kron(H, I)` → `np.kron(I, H)` 等

### 3. ClassicalGKSLBosonSimulator → exact Liouvillian expm（拡張空間）

- 同じexact expm方式を拡張電子+フォノン空間に適用
- 部分トレースで電子系ρ_elを抽出して観測量を計算
- rho_finalにはρ_elを返す（他のボソンシミュレータと統一）

### 4. QuditGKSLBosonSimulator / QubitGKSLBosonSimulator の rho_final 修正

- `rho_final: rho` → `rho_final: partial_trace_phonon(rho, dim_el, dim_ph)`
- これによりIssue 5, 6が同時に解消される

### 修正しない項目

- QubitGKSLSimulator / QuditGKSLSimulator: 既に正常動作、Stinespring+Trotterは正しい
- ショット系シミュレータ: 既に正常動作
- gksl_validation.py: 閾値は物理的に妥当
- GKSLPhysicalParameters: パラメータ検証は正常

- classical_boson と qudit_boson も同様に若干の差異
- 全シナリオで CPTP 保存（正値性 PASS）
